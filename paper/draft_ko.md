## 초록 (요지)

대규모 씬의 3DGS 학습은 GPU 메모리를 초과하며, 기존 해법은 전부 실패를 **예방**하려 한다: 휴리스틱 사전 분할, 가우시안 예산 상한, out-of-core 스트리밍. 우리는 반대의 실용적 입장을 취한다 — **VRAM을 계산하지도 감시하지도 말고, OOM이 터지면 그것 자체를 분할 신호로 쓴다.** 씬을 단일 타일로 학습하다 OOM이 나면 실패를 3종으로 분류(즉시 용량 초과 / 파편화 / densification 성장)하여 대응한다: 파편화는 제자리 재시도, 나머지는 타일을 쪼개 재큐잉. 성장형 OOM에서는 크래시 순간 전 rank의 학습된 가우시안을 공유메모리+시그널로 긴급 저장·병합하여 자식 타일이 **부모의 부분 재구성을 상속(warm-start)** 한다 — 학습 진행분을 버리지 않는다. 분할이 반응형이므로 메모리 모델도, 프로파일링도, 씬별 튜닝도 불필요하다: 같은 명령이 어떤 GPU 수·메모리에서든 무인 완주하며, 하드웨어가 요구하는 깊이만큼만 재귀한다. 나아가 기하 중점 분할이 체계적 자식 불균형(우리 씬에서 2.1~2.3배)을 만들고, SfM 포인트 밀도는 최종 가우시안 밀도의 나쁜 예측자임(r=0.28)을 보여 프록시 기반 균형화를 기각한다; 대신 **실제 학습된 가우시안 분포의 median**에서 자르면 불균형이 ≤1.03배로 준다. 30카메라 도심 씬에서 66M 가우시안 재구성을 2.5일간 완전 무인으로 완주했고, 성장형 OOM 13회를 데이터 손실 없이 통과했다.

## 1. 서론

**주장 5개 (각각 검증 위치 명시):**

1. **OOM 반응형 타일링** — VRAM 추정·감시·사전 프로파일링 없음. 실패가 곧 신호. (§3.2, §4.2)
2. **실패의 분류학** — 모든 OOM이 "분할하라"가 아니다: 즉시 용량 / 파편화 / 성장은 다른 대응을 요구. (§3.1)
3. **크래시 내성 warm-start 핸드오프** — 학습된 가우시안이 크래시를 넘어 자식의 초기값이 됨. 처음부터 재학습 없음. (§3.3)
4. **실측 median 분할** — 면적도 SfM 프록시도 아닌, 학습된 가우시안 분포로 균형화. clamp로 종료 보장. (§3.4, §4.3)
5. **무인 완주가 1급 목표** — 실무자가 원하는 성질: 한 번 실행하면, 있는 GPU에서, 씬이 나온다. (§4.1)

**한 문장 포지셔닝:** 기존 연구는 메모리 실패를 *예측·회피*하는 데 노력을 쓴다; 우리는 그 노력을 전혀 쓰지 않고, 실패에 *반응*하는 것이 더 단순하고 하드웨어 불문이며 아무것도 잃지 않음을 보인다.

## 2. 관련 연구 (4축)

- **사전 분할 대규모 3DGS** — VastGaussian, CityGaussian(V2), DOGS, Hierarchical-3DGS, HRGS, BlockGaussian. 전부 학습 **전에** 카메라 위치·SfM 밀도·공간 휴리스틱으로 나눔; 블록 크기를 대상 GPU에 맞춰 튜닝해야 함. BlockGaussian이 가장 가까움(content-aware 균형 블록)이나 콘텐츠를 SfM 포인트 수로 추정 — 우리가 실측 기각하는 프록시 (§4.3).
- **메모리 한정/out-of-core 학습** — Taming-3DGS 예산, Gaussians on a Diet, TideGS, CLM, A LoD of Gaussians. 구조적으로 OOM을 회피(캡·오프로딩·스트리밍); 처리량이나 품질 상한을 대가로 지불하고, 선택한 예산이 맞다는 가정은 여전히 필요.
- **ML 시스템의 반응형 메모리 관리** — DTR(ICLR'21)은 OOM 시 텐서를 버리고 재계산, 반응형 vs 계획형 패러다임을 텐서 수준에서 확립; 클러스터 스케줄러(AntMan, CARMA)는 OOM 시 재시작/오프로딩. 우리는 이 철학을 **상태 상속을 동반한 공간적 문제 분할**로 가져감: 같은 계산을 다시 하는 게 아니라, 작업 자체를 영구 분할하고 부분 결과를 상속.
- **분산 3DGS** — Grendel-GS(타일별 학습의 기반), RetinaGS, Splaxel. 직교적: 그들은 한 학습을 확장, 우리는 여러 학습을 스케줄.

## 3. 방법

### 3.1 3DGS 학습의 OOM 분류학

| 분류 | 증상 | 원인 | 대응 |
|---|---|---|---|
| Cat1 | iter ~1에서 OOM | 작업셋(이미지+SfM 초기값)이 용량 초과 | 즉시 분할; 자식은 처음부터 |
| Cat2 | densification 이전, 동일 iteration 재발 | 할당자 파편화 (reserved ≫ allocated) | 제한 횟수 제자리 재시도 후 분할 |
| Cat3 | densification 시작 이후 | 가우시안 성장 | 전 rank 긴급 저장 → 병합 → 분할 → **자식 warm-start** |
| Cat4 | 자식이 로드 시점에 OOM | 상속분 자체가 용량 초과 | 상속 유지한 채 재분할 |

분류에 필요한 것은 실패 iteration과 densification 스케줄의 상대 위치뿐 — 메모리 내부 관측 불필요.

### 3.2 반응형 재귀 타일링

타일은 지면(X/Y) 위 이진 트리. 수렴(best+patience 조기종료) 또는 OOM까지 학습; OOM이면 자식 둘을 큐에 넣는다. 종료 보장은 (a) 분할비 clamp(§3.4), (b) 최소 타일 크기. 스케줄러는 영속 작업 큐(`adaptive_state.json`) — 덕분에 어떤 중단 후에도 전체 파이프라인이 재개 가능.

### 3.3 크래시 내성 warm-start 핸드오프 (Cat3)

OOM 순간 rank들은 collective에 묶여 있을 수 있어 NCCL을 쓸 수 없다. 감지 rank가 실패 기록(분류·iteration·분할 좌표 §3.4)을 사전 매핑된 공유메모리 파일에 쓰고 동료에게 SIGUSR1; 각 rank는 자기 shard를 두 자식 bbox로 걸러 rank별 PLY 저장; 래퍼가 자식별로 병합·개수 검증. 자식은 병합본을 연속 구간으로 재샤딩해 재개.

실전에서 필요했던 엔지니어링 (각각 관찰된 실패에서 역추적):
- **종료 신호에 대한 저장 가드.** torchrun은 한 rank가 종료하면 나머지에 SIGTERM을 쏜다; 순진한 핸들러는 진행 중인 저장을 처음부터 재시작했고, 대형 타일에서 재시작이 유예시간을 넘겨 rank 파일 하나를 유실(19회 중 1회 관찰). 저장중 플래그를 세워 핸들러가 비켜서게 하면 중단된 저장이 그 지점부터 재개된다. 시그널 주입 테스트로 검증.
- 저장 경로의 **fallback 상태 기록** — 감지 rank의 monitor 스레드가 메인 스레드의 상태 기록을 앞지르는 레이스 (수정 전 발생률 ~100%).
- 수렴 판정을 opacity-reset 없는 구간으로 게이팅 (아니면 리셋 중 저장돼 타일이 검게 나옴).

### 3.4 실측 가우시안 median 분할

중점 분할은 콘텐츠 무지: 우리 씬에서 일관되게 ≈32/68 자식 불균형을 만들고, 밀집 자식이 로드만으로 재OOM → 최소 크기 바닥까지 연쇄 → *skipped* = 최종 씬의 영구 구멍. 균형화엔 콘텐츠 위치를 알아야 하는데, SfM 포인트 수는 모른다(타일별 SfM 수 vs 최종 가우시안 수 r=0.28; SfM 희박 구역이 오히려 더 붊 — densification이 extractor 편향을 보상). 학습된 가우시안 자체가 정답이고 OOM 순간 이미 메모리에 있다: 긴 축 좌표의 median에서 자르되, 큰 자식이 부모 폭의 65%를 넘지 않게 clamp(종료 보장). 감지 rank가 표본으로 절단 위치를 계산해 같은 공유메모리 채널로 전파 — 전 rank가 동일한 자식 box로 필터.

## 4. 실험

**셋업.** 30카메라 도심 항공 씬(삼성동); 2–3× Quadro RTX 6000 24GB; Grendel-GS 분산 백엔드; 품질 런은 vanilla densification, OOM 스트레스 ablation은 공격적 스케줄.

### 4.1 무인 완주 (시스템 실증)
7/27 품질 런: 37 타일(19 leaf), Cat3 13회, rank 파일 유실 0, skipped 0, 66.1M 가우시안 병합 — 2.5일, 사람 개입 0. 3-GPU(홀수 world size) 스모크: Cat3 전체 사이클 검증, 62개 속성 비트 단위 병합 검증 포함.

### 4.2 OOM 분류학의 실증
스트레스 런: Cat1은 iter 1(이미지 작업셋), Cat2는 고정 iteration 재발(파편화; 재시도는 전진할 때만 유효), Cat3는 densification 이후. 파편화 완화(할당자 GC 임계 + max split size)로 루트 타일 생존 79 → 3500 iteration.

### 4.4 무제약 oracle 대비 오버헤드 **[TODO — 설계 완료, 미실행]**

메모리 반응형 방법의 이상적 기준선은 *메모리 제약이 아예 없는* 학습이다. 이를 명시적으로 구성한다: 씬 **A**를 "원본 single-tile Grendel-GS가 **C**개 GPU로는 완주(oracle: 시간 **D**, 품질 **Q**, 개수 **E**)하지만 2개 GPU로는 안 들어가는" 크기로 잡고, 같은 머신에서 Split-on-Failure를 2 GPU로 — 강제로 타일링되게 — 돌려 같은 held-out 품질 **Q** 도달 시간을 잰다. 정규화 오버헤드:

> **overhead = (T_ours × 2) / (D × C)** (GPU-hours 비율; 1.0 = 이상)

도착 기준은 개수 E가 아니라 품질 Q — 타일 학습은 경계 중복·box 밖 폐기로 개수 궤적 자체가 다르다. E는 보조 지표.

1.0은 구조상 도달 불가 — OOM 전 iteration 폐기, Cat1/2 재시작, warm-start 재수렴, 큐 직렬화가 전부 순수 비용. 따라서 이 절의 주장은 오버헤드 0이 아니라 **"oracle이 아예 못 쓰는 하드웨어에서, 측정된 X%의 프리미엄으로 완주"**. X의 분해(폐기 iteration / 재시작 / 재수렴 / 스케줄 공백)는 런 로그에서 산출해 함께 보고.

명시할 성질: 씬이 들어가면 Split-on-Failure는 발동하지 않고 기반 Grendel-GS와 동일 — **작은 씬은 공짜, 큰 씬은 X% 내고 무인 완주.**

*우리 하드웨어 계획: A = mini_30 해상도 축소판(8× 24GB single-tile은 들어가고 2×는 안 들어가게 보정); oracle C=8; ours 2 GPU, 중점/median 두 모드.*

## 5. 한계
